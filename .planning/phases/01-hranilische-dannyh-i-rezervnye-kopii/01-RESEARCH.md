## Краткий вывод

Для основного состояния резюме и нескольких связанных версий рекомендуется IndexedDB за узким интерфейсом репозитория: API хранит структурированные объекты асинхронно и поддерживает транзакции; `localStorage` синхронен и хранит строки, поэтому его лучше оставить для небольших настроек интерфейса. [CITED: https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API] [CITED: https://developer.mozilla.org/en-US/docs/Web/API/Web_Storage_API]

Импорт должен сначала полностью пройти синтаксическую и структурную проверку и построить безопасный предпросмотр. До явного подтверждения не выполнять записей. При подтверждении заменить всё состояние одной транзакцией IndexedDB; не разделять очистку старых записей и запись новых между транзакциями. Ошибка разбора, схемы, миграции или записи должна оставлять старое состояние доступным. [CITED: https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API/Using_IndexedDB] [CITED: https://developer.mozilla.org/en-US/docs/Web/API/IDBTransaction]

**Основная рекомендация:** ввести явную версию формата резервной копии, проверить весь импорт до записи, а восстановление выполнять одной транзакцией. Само браузерное хранилище не является резервной копией: браузер может удалить best-effort данные, поэтому экспорт и понятные ошибки хранения остаются важны. [CITED: https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria]

## Архитектурные паттерны

### Поток импорта

```text
Файл, выбранный пользователем
  → ограничение размера и чтение текста
  → JSON.parse (ошибка: остановить без записи)
  → проверка конверта, версии схемы и инвариантов
  → миграция поддерживаемой старой версии в текущую модель
  → безопасная краткая сводка для предпросмотра
  → подтверждение замены (и предложение скачать текущую копию)
  → одна readwrite-транзакция IndexedDB: заменить набор данных
  → успех только после transaction complete
```

Проверка, преобразование и составление предпросмотра должны завершиться до открытия write-транзакции. Внутри IndexedDB транзакции делать только операции хранилища: документация предупреждает, что транзакция может стать неактивной при возврате в event loop без запросов; ожидание внешних асинхронных действий внутри транзакции ненадёжно. [CITED: https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API/Using_IndexedDB]

Для замены нескольких записей открыть одну `readwrite` транзакцию со всеми нужными store, выполнить очистку и запись набора в той же транзакции. В случае abort все изменения откатываются; завершение подтверждать событием `complete`, а не успешностью последнего отдельного запроса. [CITED: https://developer.mozilla.org/en-US/docs/Web/API/IDBTransaction] [CITED: https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API/Using_IndexedDB]

### Минимальный конверт резервной копии (иллюстративный)

```json
{
  "format": "resume-backup",
  "schemaVersion": 1,
  "exportedAt": "2026-11-04T00:00:00.000Z",
  "data": {
    "masterResume": null,
    "versions": []
  }
}
```

Это пример структуры, не утверждённый контракт. `format`, `schemaVersion`, `exportedAt`, `data`, `masterResume`, `versions` — иллюстративные значения с пометкой [ASSUMED]; planner может выбрать имена, обязательность master resume и детализацию модели, учитывая, что редактор резюме будет в фазе 2, а версия и связь с вакансией описаны будущей фазой 4. Не включать полный текст вакансии в экспорт, когда пользователь выбрал исключение; сохранять timestamps версий согласно D-06.

### Версионирование и проверка

- Проверять форматный маркер и номер схемы до чтения доменной нагрузки. Неизвестная будущая версия — отклонить с сообщением об unsupported format, не пытаться угадывать или частично применять. [ASSUMED]
- Для каждой поддерживаемой старой схемы применять явную чистую миграцию `old → current`; затем проверять результат уже по текущим инвариантам. Не использовать «принять любую JSON-структуру». [ASSUMED]
- JSON Schema `format` может быть только аннотацией: спецификация допускает его поведение как annotation по умолчанию, а assertion vocabulary — опциональна. Критичные форматы дат поэтому проверять прикладной логикой, если библиотека не настроена на assertion. [CITED: https://json-schema.org/draft/2020-12/json-schema-validation]
- Для unknown fields выбрать явную политику: строгий отказ либо безопасное игнорирование только полей, разрешённых версией. Не передавать импортированный объект в `Object.assign`/deep merge текущего состояния. Это мера защиты от неучтённых полей и прототипных ключей. [ASSUMED]
- Проверять, что структура JSON соответствует ожидаемому типу; идентификаторы уникальны; массивы и строки имеют допустимые пределы; даты разбираются и согласованы; при выборе экспорта без текста вакансии текст действительно отсутствует. Конкретные верхние лимиты размера/длины подобрать в задаче по модели и безопасно отклонять превышение. [ASSUMED]

### Текущие данные и резервная копия перед заменой

1. До экспорта текущего состояния предложить пользователю скачать копию; отмена скачивания/замены оставляет состояние неизменным.
2. Для запуска экспорта показывать предупреждение D-08 каждый раз и собирать выбор о тексте вакансии D-05 в рамках каждого экспорта.
3. Экспортировать основное резюме и все версии. Имена компании/вакансии и даты версий включаются как метаданные, если они существуют; вопрос о тексте вакансии регулируется per-version выбором пользователя.
4. Формировать имя файла по локальной текущей дате в виде `resume-backup-YYYY-MM-DD.json`, согласно D-07; определить используемую часовую зону приложения в реализации, чтобы избежать сдвига даты около полуночи. Последний риск отмечен [ASSUMED].

## Безопасность и приватность

Данные IndexedDB изолированы политикой same-origin, но это не следует трактовать как шифрование: все скрипты, исполняемые на origin приложения, входят в его границу доверия. IndexedDB обычно хранит данные best-effort; браузерные квоты и решение об удалении зависят от браузера. [CITED: https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API] [CITED: https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria]

Основные угрозы для плана: подмена данных невалидным JSON (tampering), чрезмерно большой/глубокий файл (denial of service), вывод недоверенных строк как HTML (XSS при небезопасном рендеринге), случайное раскрытие вакансии или личных данных в резервном файле (information disclosure). Меры: ограничить размер до чтения/разбора, структурно и семантически валидировать, показывать поля текстом, не записывать до подтверждения, транзакционно заменять полный набор, по умолчанию следовать явному выбору D-05, показывать D-08 и не отправлять данные на сервер. Эти назначения STRIDE/меры — предварительные рекомендации [ASSUMED], планировщик должен оформить требуемый threat model для фазы.

## Вопросы для планирования

Новых пользовательских решений для начала планирования не требуется. Плану нужно зафиксировать реализационные детали в рамках предоставленной агенту свободы: имя и точную схему backup; модель данных уровня основы без преждевременной реализации редактора; поддерживаемые версии/миграции; структуру IndexedDB store; допустимый размер импорта; тестовый runner после выбора приложения. Эти пункты не меняют D-01—D-08.
